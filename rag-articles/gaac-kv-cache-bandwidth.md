# 模型装得下，为什么还是跑不快？

这两年，本地大模型部署的门槛已经降了不少。

过去讨论一台电脑能不能运行某个模型，首先看的往往是显存容量。一个 32B 模型，原始精度放不下，就换成 8-bit；8-bit 还是太大，就继续压到 4-bit。只要权重能够完整加载，模型就算是跑起来了。

但实际使用中经常会遇到另一种情况：模型确实装进了内存，生成速度却远没有想象中理想。尤其是接入长文档、代码仓库，或者连续进行多轮对话之后，原本还算流畅的输出可能逐渐变慢。

这时候再去看设备的硬件参数，问题就变得有些奇怪。GPU 的理论算力并不低，模型也没有超出内存容量，为什么生成一个 token 仍然需要这么长时间？

2026 年 10 月 28 日，Notre Dame 的研究人员发布了一篇预印本：[GAAC: Lossless KV Compression for Bandwidth-Efficient LLM Inference on Personal Devices](https://arxiv.org/html/2610.38210v1)。

这篇论文研究的是一种用于 KV Cache 的无损压缩方案。它能让 BF16 格式的 KV Cache 在实际驻留内存中减少约 26% 的占用，同时提高长上下文注意力计算的速度。

但我更感兴趣的是另外几个数字。

在 NVIDIA DGX Spark 上，GAAC 把长上下文注意力内核加速了 1.19–1.27 倍。换成包含模型计算的完整 decode step，提升却只有 1.04–1.15 倍。而在固定 KV 内存预算、允许增加并发请求的测试中，系统总吞吐量又提高了 13%–29%。

同一项优化，内存节省、单步加速和并发吞吐给出了三个差异很大的结果。

这不是一个需要掩饰的实验缺点。恰恰相反，它把大模型推理系统中一个很容易被忽略的问题摆到了台面上：

我们究竟在优化什么？

模型能够装进内存，说明容量问题暂时解决了。模型生成得快不快，取决于执行路径上的计算和数据访问。至于同一台设备能同时处理多少请求，则还涉及内存管理、Batch 和调度策略。

这三件事相互关联，却不能简单地互相换算。

## 一、模型权重变小以后，内存问题并没有结束

讨论本地推理，很多人首先想到的是模型量化。

这很自然。模型参数的存储成本比较直观。以一个 8B 参数模型为例，如果只粗略计算权重本身，BF16 需要约 16GB，4-bit 则约 4GB。实际部署还会涉及量化元数据、运行时缓冲区等额外开销，但总体上，降低权重位宽确实能显著减少内存需求。

问题在于，模型权重不是推理时唯一需要驻留的数据。

Transformer 在生成文本时，还会保留此前 token 产生的 Key 和 Value。这就是 KV Cache。

它的作用是避免每生成一个新 token，都重新计算全部历史 token 的 K、V 表示。

例如，用户输入了一个很长的文档，模型完成 Prefill 之后，便已经得到了历史 token 对应的 KV Cache。接下来生成新 token 时，可以直接复用这些结果。

听起来似乎已经很高效了。

但 KV Cache 只解决了重复计算的问题，并没有消除历史信息的读取成本。

对于标准的全注意力机制，每生成一个新 token，仍然需要让当前 Query 与此前保存的 Key 进行注意力计算，再使用对应的 Value 得到输出。

上下文越长，需要访问的历史 KV 数据通常也越多。

更重要的是，KV Cache 的大小并不由模型参数量单独决定。它还取决于层数、KV Head 数量、每个 Head 的维度、上下文长度和数据精度。

对于典型的全注意力模型，可以用一个近似公式描述单条序列的 KV 存储成本：

`KV Bytes = 2 × Layers × KV Heads × Head Dim × Context Length × Bytes per Element`

最前面的 2 分别代表 Key 和 Value。

假设一个模型有 32 层、8 个 KV Head，每个 Head 的维度是 128，KV 使用 BF16 存储。那么每个 token 对应的 KV 数据约为 128KiB。

当上下文达到 64K token 时，一条序列的 KV Cache 就需要约 8GiB。

注意，这只是一个假设架构下的理论缓存大小，还没有算模型权重、运行时缓冲区以及内存管理开销。

如果同时处理四条类似长度的序列，KV Cache 的需求还会继续增加。

这就解释了一个经常出现的现象：一个模型在短对话中完全没有内存压力，换成长上下文、多请求的工作负载之后，资源需求却迅速膨胀。

而且，权重量化越激进，KV Cache 在总内存中所占的比例反而可能越高。

原本模型的权重占据了绝大部分内存。现在权重通过 4-bit 量化缩小了，KV Cache 却可能仍然保留在 BF16 精度下。

瓶颈并没有消失，只是转移了位置。

当然，并不是所有模型都会按上述比例增长。GQA、MQA、滑动窗口注意力、混合注意力等结构，本来就在尝试降低 KV 存储和读取成本。

这也意味着，不能只根据模型参数量判断长上下文推理的内存需求。两个参数量接近的模型，实际 KV Cache 大小可能相差不少。

到这里，我们只解释了为什么内存会被占满。

更麻烦的是，即使这些数据全部放得下，读取它们仍然需要时间。

## 二、GPU 有算力，不代表数据能及时送到

我觉得理解推理性能，最容易被忽略的就是数据搬运。

我们习惯用 TFLOPS 衡量 GPU 的计算能力，却很少同时关注内存带宽。

事实上，GPU 执行计算需要不断从不同层级的存储中获取数据。设备内存能够容纳多少数据，和计算单元每秒能够得到多少数据，是两个不同的问题。

可以把这个问题简化为两种瓶颈。

一种是 Compute-bound，即计算受限。计算单元已经非常忙碌，继续提高内存带宽也很难让任务明显加快。

另一种是 Memory-bound，即内存带宽受限。计算单元有能力处理更多数据，但数据供应跟不上。

在后一种情况下，增加理论算力未必有用。

这不是大模型特有的问题。GPU 性能分析中经典的 Roofline Model，讨论的就是计算吞吐、内存带宽与计算强度之间的关系。

计算强度可以理解为：每搬运一个字节的数据，能够完成多少计算。

如果一个操作需要大量读取数据，却只进行少量计算，它就更容易受带宽限制。

大模型的 Prefill 和 Decode，恰好能体现这种差异。

Prefill 需要处理大量输入 token，通常可以利用矩阵运算的并行性。Decode 则是逐 token 生成，每一步的计算规模和数据复用方式都不同。

尤其是在单请求、小 Batch 的情况下，模型可能需要不断读取权重和历史 KV Cache，却没有足够多的并行计算来充分利用 GPU。

对于长上下文，全注意力层还会反复读取不断增长的历史缓存。

这里有一个很关键的事实：

把 8GB 数据放在内存里，不意味着访问它不需要成本。

假设一段执行路径确实需要从设备内存读取 8GiB 数据，而可用带宽为每秒 1TB。那么仅这部分数据传输，就有数毫秒级的理论时间下限。实际执行还会受到带宽利用率、访存模式和其他开销的影响。

每生成一个 token，都可能重复发生类似的读取。

于是，即使模型权重已经压得很小，长上下文 Decode 仍然可能受限于数据搬运。

这也是为什么大模型推理优化不能只考虑 FLOPs。

2022 年的 FlashAttention 论文已经很清楚地说明了这个方向。它并没有依靠简单删除注意力计算来获得性能优势，而是重新组织计算和内存访问，减少不同存储层级之间的读写。

FlashAttention 的核心贡献之一，是让注意力计算具有更好的 IO Awareness。

GAAC 延续了类似的思路，只不过它把问题推进到了 KV Cache 的数据表示本身。

既然反复读取历史 KV 是瓶颈，那么能不能先把这些数据压小一点？

答案看似简单，但真正困难的部分在后面。

数据压缩以后，计算时还要把它还原出来。

如果压缩节省的读取时间，还不够支付解压缩的成本，优化就失去了意义。

## 三、GAAC 的关键不是压缩，而是让压缩数据直接参与计算

GAAC 的完整名称是 Group-Adaptive Additive Codec。

它的基本思路并不复杂：利用 BF16 浮点数中指数位的冗余，以较少的位数保存指数，再在注意力计算时恢复原始数值。

一个 BF16 浮点数包含 16 位：

- 1 位符号位；
- 8 位指数；
- 7 位尾数。

从存储格式来看，每个数值都有 8 位指数。但在真实模型产生的 KV 数据中，指数并不会均匀地覆盖所有可能取值。

很多通道中的指数集中在一个相对狭窄的连续区间。

GAAC 正是利用了这一点。

它保留原始符号位和尾数，只对指数进行编码。对于每个通道，先通过校准确定常见的指数区间，再把指数表示为相对于区间基值的偏移。

如果一个指数可以落在连续 8 个值的范围内，就只需要 3 位表示偏移。如果需要覆盖连续 16 个值，就使用 4 位。无法放进这些范围的情况，则回退到原始 8 位指数。

GAAC 每 8 个元素组成一个 Group，并通过少量元数据标记这一组使用哪种编码模式。

论文报告，在测试的五个模型中，约 88%–90% 的 Group 可以使用 3-bit 模式，真正需要回退到原始指数的比例很低。

这样一来，原本每个元素占用 16 位的 BF16 数据，在常见编码模式下可以下降到约 11.25 位，包含模式标签的摊销成本。

再考虑额外的编码和存储开销，论文测得的平均压缩比约为 1.405–1.407 倍。

这里有一个容易算错的地方。

1.406 倍的压缩比，并不是节省 40.6% 的空间，而是压缩后的数据体积约为原来的 71.1%，节省约 28.9%。

实际部署还需要固定容量的存储槽、块表、回退数据等结构，所以最终的驻留 KV 内存节省约为 26%。

这种区分很重要，因为它说明压缩算法得到的数据体积，和运行时真正能够释放的内存，并不完全相同。

不过，GAAC 最值得研究的地方还不是编码方式。

它真正解决的是：压缩过的 KV Cache，应该怎样被读取。

最直接的实现方案，是先从内存中取出压缩数据，完整解压，再把恢复后的 KV 交给注意力算子。

但这么做会产生额外的数据搬运。

系统不仅要读取压缩数据，还要写出解压后的数据。后续注意力计算又需要读取这些完整数据。

原本想省掉的内存流量，很可能被解压过程重新引入。

GAAC 换了一种方式。

它把 KV 重建过程融合进 Attention Kernel。计算时，内核直接读取压缩的 KV 数据块，在内部恢复当前需要的 BF16 数值，然后立即参与注意力计算。

整个过程不需要先在设备内存中生成一份完整的解压缓存。

这里的关键不是“解压缩特别快”，而是数据恢复和消费发生在同一条执行路径上。

恢复后的数据不必重新落回外部内存。

为了支持持续生成，GAAC 还采用了按 Block 压缩的方式。

新 token 产生的 KV 首先写入尚未填满的 BF16 Block。等一个 Block 写满之后，才进行压缩。此后，这个 Block 就作为历史缓存保留下来，不会因为后续又生成了新 token 而反复压缩。

这种 Fill-then-finalize 的设计，避免了每生成一个 token 就重新打包整块缓存。

同时，GAAC 使用固定容量的压缩存储槽和原始 BF16 Block 两种存储形式。压缩结果超出槽容量时，可以直接保留原始数据。

这些设计看起来不如压缩率醒目，却决定了一个算法能否真正进入持续运行的推理系统。

模型推理不是对静态文件做一次离线压缩。KV Cache 会不断追加、分配、读取和释放。如果压缩算法没有考虑这些操作，理论上的节省很容易被运行时开销抵消。

对我来说，这也是 GAAC 比单纯提出一种新编码格式更有价值的地方。

它没有停留在数据结构层面，而是尝试让数据表示、计算内核和缓存管理彼此配合。

## 四、少搬运了 294 微秒的数据，最终只省下 245 微秒

GAAC 的实验里，有一组时间分解特别值得看。

作者在 DGX Spark 上，对 64K 上下文的一次 Decode Attention 进行了拆解。实验比较了使用原始 BF16 KV 的 FlashAttention-2、先解压再计算的方案，以及融合解压过程的 GAAC。

结果如下，单位是微秒：

| 耗时项目 | 原始 FA2 | GAAC |
|---|---:|---:|
| KV 数据读取 | 1117.8 | 823.5 |
| 计算及融合重建 | 241.5 | 290.7 |
| 总耗时 | 1359.3 | 1114.2 |

数据来源：GAAC 论文 Table 5。

读取 KV 的时间减少了 294.3 微秒。

与此同时，额外的数据重建让计算部分增加了 49.2 微秒。

两者抵消之后，最终净节省约 245 微秒，得到 1.22 倍的注意力内核加速。

这个结果很有意思。

GAAC 实际上是在主动增加计算量。

在通常的性能优化思路中，我们会倾向于减少计算，避免执行额外操作。但在这里，增加一些轻量计算反而能够降低总耗时，因为它换来了更大幅度的数据读取成本下降。

这说明，当系统受内存带宽限制时，最优解未必是计算最少的方案。

更直接的证据来自另一个实验。

如果不进行内核融合，而是先完整解压 KV，再运行普通注意力计算，总耗时达到约 2290 微秒。

它甚至比原始 FA2 的 1359 微秒慢了很多。

两种方案都采用了压缩数据，但最终性能完全不同。

区别在于数据什么时候被还原、还原以后保存在哪里，以及后续计算是否需要重新读取。

单看压缩率，根本无法预测这种差异。

GAAC 的消融实验还给出了一个更有意思的反例。

作者尝试增加 2-bit 编码模式，让压缩比从 1.406 倍提升至 1.439 倍。结果压缩率只改善了约 2.3%，解码耗时却从 187.1 微秒增加到 526.7 微秒，接近原来的 2.8 倍。

压得更小，反而更难高效读取。

这让我想到一个比压缩率更有用的评价标准：

对于会被反复读取的数据，不能只计算它存储时占多少空间，还要计算它在整个生命周期里被消费了多少次，每次消费需要付出多少代价。

一个文件放在磁盘里，可能只需要解压一次。

但 KV Cache 不同。历史数据可能在后续的许多 Decode Step 中反复参与注意力计算。

这意味着压缩格式的读取效率，往往比额外节省的几个百分点更重要。

一个真正适合推理的压缩方案，需要同时考虑编码成本、数据布局、访问粒度、解码成本和内核实现。

这些因素共同决定最终速度。

## 五、为什么内核快了 22%，整个模型却只快了几个百分点？

前面的 1.22 倍，是注意力内核的加速结果。

如果直接把它写成“模型推理速度提高 22%”，就犯了一个典型错误。

因为 Attention Kernel 只是完整 Decode Step 的一部分。

一次 Decode Step 还需要执行模型中的其他运算，包括权重读取、线性层、MLP、归一化、各种调度和运行时操作。对于 MoE 模型，还可能涉及专家路由及相关计算。

优化某一个环节，无法让其他部分自动变快。

这个问题可以用 Amdahl 定律解释。

假设一次完整 Decode Step 中，Attention 占据了 40% 的执行时间。现在我们把这部分加速到 1.22 倍，其余 60% 保持不变。

那么整体加速比是：

`Speedup = 1 / (0.6 + 0.4 / 1.22) ≈ 1.078`

也就是说，Attention 快了 22%，完整步骤只快了约 7.8%。

这里的 40% 是为了说明原理而设定的假设值，并不是 GAAC 实验测得的固定比例。

真正决定整体收益的，是被优化部分原本占据了多少时间。

在 GAAC 的实验中，这个差异表现得很明显。

DGX Spark 上，64K 上下文的注意力内核获得了约 1.19–1.27 倍加速。但换成完整 W4A16 Decode Step，测试范围内的收益只有 1.04–1.15 倍。

对于某些混合注意力和 MoE 模型，加速幅度更是只有约 4%–6%。

原因并不难理解。

GAAC 测试中的这些混合架构，只有四分之一的层采用全注意力。相对于整个模型的计算和权重访问，能够从全量历史 KV 读取中获益的部分比较有限。

于是，同样的压缩算法，在不同模型架构上产生了不同的实际效果。

还有一个细节值得注意。

GAAC 主要改变的是长上下文 Decode 中的数据读取成本。

可以用一个简化关系来理解单步耗时：

`T_decode(L) ≈ T_fixed + αL + T_codec(L)`

其中，`L` 是上下文长度，`T_fixed` 代表与上下文长度关系较小的开销，`αL` 近似表示随上下文增长的历史数据访问成本，而 `T_codec(L)` 是压缩和重建带来的额外成本。

这不是所有模型都适用的精确性能公式，但很适合解释这里发生了什么。

当上下文很短时，历史 KV 读取成本不大，额外的编码和重建可能占据较高比例。

随着上下文增长，读取成本逐渐增加，压缩带来的收益才会变得明显。

换句话说，GAAC 更像是在改善长上下文 Decode 的增长成本，而不是把整个推理过程统一加速一个固定比例。

这也解释了为什么短上下文、少量并发的场景，未必能够充分发挥它的优势。

对用户体验来说，另一个问题是 Prefill。

长文档请求通常需要先处理大量输入，才能开始输出第一个 token。GAAC 的融合加速主要作用于 Decode，而 Prefill 仍然使用常规注意力路径。

因此，它不能直接解决所有长上下文请求的首 token 等待问题。

如果一个请求主要耗时都发生在 Prefill，之后只生成几十个 token，那么 Decode 优化即使很漂亮，对整次交互的影响也可能有限。

反过来，如果一个请求需要在长上下文基础上持续生成大量内容，Decode 的每一步都能省下一些时间，累计收益就更值得关注。

这也是为什么我认为推理性能不能只公布一个 tokens/s。

不同阶段的瓶颈不同，平均值可能掩盖实际问题。

## 六、吞吐量提高 20%，每条序列分到的速度却可能下降

GAAC 论文中，我最想展开讨论的其实不是压缩算法，而是 Table 2 的吞吐量实验。

作者在固定 KV 内存预算下，比较原始 BF16 KV 与 GAAC 能够容纳的最大并发数，以及对应的聚合生成吞吐。

以 Qwen3-8B、64K 上下文、20GB KV 预算的配置为例：

原始 BF16 KV 可以容纳 2 条并发序列，总吞吐为 19.0 tok/s。

使用 GAAC 后，可以容纳 3 条并发序列，总吞吐提高到 22.8 tok/s。

整体提升了 20%。

乍一看，这当然是不错的结果。设备不需要增加内存，就能同时处理更多请求。

但换一个角度看。

原始方案的聚合吞吐是 19.0 tok/s，平均分到两条序列，每条约为 9.5 tok/s。

GAAC 的聚合吞吐是 22.8 tok/s，平均分到三条序列，每条约为 7.6 tok/s。

这只是基于聚合吞吐和并发数的算术平均，不能用来证明 GAAC 在相同 Batch 下让单请求变慢。但它足以揭示一个容易被总吞吐掩盖的事实：

系统每秒处理的 token 更多，不等于每个活跃请求都获得了更高的生成速率。

如果一台设备只有一个人在使用，那么这位用户在意的通常是响应有多快，输出有没有明显停顿。

如果同一台设备需要运行多个 Agent，情况就不一样了。

例如，三个任务分别在进行代码分析、文档处理和测试结果总结。每个任务都有自己的上下文，需要保存和更新 KV Cache。

原本设备只能同时容纳两条长上下文序列，第三条必须等待，或者经过额外的缓存管理才能继续执行。

现在通过压缩，可以把三条都放进内存。

即使每条序列平均获得的 token 速率有所下降，整个任务组的完成效率仍然可能改善。

这不是因为单个任务一定变快了，而是系统减少了等待和资源争用带来的限制。

对面向多人或多 Agent 的推理服务来说，这类收益往往很有价值。

但如果产品面向的是低并发、实时交互的单个用户，评价标准就不能照搬。

一个聊天助手每秒能生成多少 token，与一台服务端每秒能为所有用户生成多少 token，是两种不同的指标。

更进一步，即使聚合吞吐很高，也可能存在严重的尾部延迟。

假设系统通过增加 Batch 提高了总体利用率，但部分请求因为排队或调度问题，首 token 等待时间显著增加。

用户实际感受到的服务质量可能反而下降。

这也是推理服务中 Goodput 概念越来越值得关注的原因。

普通 Throughput 统计单位时间处理了多少 token 或请求。

Goodput 则可以进一步考虑有多少工作是在规定的延迟要求内完成的。

如果一个在线助手要求及时响应，那么超出延迟目标的请求，即使最终成功生成，也不能算作完全满足了服务质量。

当然，Goodput 的具体定义需要根据产品目标制定。实时聊天、离线文档处理和后台 Agent 任务，不应该共用同一套延迟标准。

问题也由此变得清楚：

在相同硬件上提高吞吐量，并不等于改善所有使用场景。

我们需要先知道系统究竟服务于谁，再决定什么样的提升才有意义。

## 七、这不是 GAAC 独有的现象

如果把目光从 GAAC 移开，会发现类似的问题在其他推理优化技术中反复出现。

一个很典型的例子是 PagedAttention。

2023 年，UC Berkeley 等机构的研究人员在 SOSP 发表论文，提出通过类似操作系统虚拟内存分页的方式管理 KV Cache，并以此构建 vLLM。

传统 KV Cache 管理容易产生内存碎片，也可能因为预留连续空间而浪费容量。PagedAttention 让逻辑上连续的 KV 数据，可以通过块表映射到不连续的物理存储块。

这样既减少了内存浪费，也让不同请求之间的缓存共享更加灵活。

论文在当时的基线与测试条件下，报告了约 2–4 倍的吞吐提升，同时保持相近的延迟水平。

但这并不意味着 PagedAttention 把模型中的数学运算加速了几倍。

它的一大贡献是改善内存利用率，让服务系统能够更有效地组织并发请求。

这和 GAAC 的思路有相似之处，也有明显区别。

PagedAttention 主要解决 KV Cache 如何分配、管理和共享。

GAAC 则进一步研究 KV Cache 以什么形式存储，以及注意力计算如何直接使用压缩后的数据。

两者都说明，推理系统的性能并不只取决于矩阵计算有多快。

不过，真正能与 GAAC 形成鲜明对照的，是 FP8 KV Cache。

FP8 的思路更加直接：把原本使用 BF16 存储的 KV Cache 转换为 8-bit 浮点格式。

从存储位宽来看，这相当于把 KV 数据体积减半。

与 GAAC 的无损压缩不同，FP8 涉及数值精度变化。因此，除了性能之外，还需要验证模型输出质量。

2026 年 4 月，vLLM 团队发布了一篇很有参考价值的工程报告：[The State of FP8 KV-Cache and Attention Quantization in vLLM](https://vllm.ai/blog/2026-04-22-fp8-kvcache)。

这份报告没有只展示某个 Kernel 的峰值加速，而是分别测试了单请求延迟、并发负载和模型精度。

其中一组结果非常能说明问题。

在 H100 上，针对 Llama-3.1-8B，经过优化的 FP8 方案把单请求 Decode ITL 随上下文长度增长的斜率，降低到了 BF16 基线的约 54%。

这说明它明显降低了长上下文带来的边际解码成本。

但在另一组 150 个请求、并发数为 8、每条请求包含约 20K 输入 token 和约 2K 输出 token 的测试中，聚合输出吞吐只从 450.3 tok/s 增加到 517.5 tok/s。

提升约 14.9%。

KV 存储位宽减半，长上下文 ITL 的增长斜率明显改善，最终系统吞吐却只提高了不到 15%。

如果看另一种模型，反差更大。

对于 gpt-oss-20b，vLLM 测得的 FP8 方案在跳过滑动窗口层量化后，聚合吞吐提升约 4.8%。

也就是说，即使采用了更激进的 KV 精度压缩，完整系统也未必获得很大的吞吐提升。

这是一个比 GAAC 更有力的外部印证：容量节省与执行速度之间，确实不存在固定的换算比例。

原因还是模型架构、计算路径和运行时负载。

在一个已经较少依赖全量历史 KV 读取的模型中，即使进一步缩小缓存，能优化的耗时比例也比较有限。

vLLM 的报告还暴露了另一个问题。

在早期测试中，Hopper 平台上的 FP8 注意力计算存在长上下文数值累积精度问题。一个 128K 的 Needle-in-a-Haystack 测试中，准确率曾从 BF16 基线的 91% 降至 13%。

团队后来通过改进累积方式，把准确率恢复到约 89%，但额外的累积操作也带来了寄存器压力和部分 Prefill 性能问题。

这件事让我觉得，比较压缩方案时，单纯问“哪个压得更小”没有太大意义。

FP8 的优势是能够显著减少 KV 数据位宽，并在合适的硬件和内核实现上获得性能收益。

GAAC 则试图保留 BF16 KV 的原始数值，通过利用指数冗余来减少数据搬运。

两者的目标并不完全一致。

GAAC 的论文还测试了在已经量化成 FP8 的 KV 数据上进行进一步无损压缩。对于 E4M3 格式，额外压缩比只有 1.09–1.14 倍，远低于直接压缩 BF16 的结果。

这也符合直觉：数据已经经过一次大幅压缩，剩余可利用的冗余自然更少。

所以，如果部署环境本身就采用高效的 FP8 KV Cache，GAAC 在 BF16 上取得的数字就不能直接拿来预测增量收益。

反过来，如果应用对数值变化比较敏感，或者硬件没有足够成熟的 FP8 注意力支持，无损方案可能有自己的价值。

需要比较的是完整运行条件，而不是论文里最大的一个数字。

## 八、长上下文越长，压缩就一定越值得吗？

从目前的实验结果看，GAAC 的收益确实更偏向长上下文。

但我觉得这里还可以继续追问。

首先，长上下文不一定意味着 KV 读取始终是主要瓶颈。

不同模型采用不同的注意力结构。即使上下文长度相同，完整 Decode Step 中 KV 读取的占比也可能不同。

其次，长上下文的负载形式差别很大。

一种情况是输入 64K token，然后持续生成几千个 token。

另一种情况是输入 64K token，只要求模型回答一句话。

前者需要经过大量 Decode Step，单步性能提升能够不断累积。

后者可能主要耗时在 Prefill 和首 token 等待。即使后续 Decode 每一步快了不少，整次请求的完成时间也未必明显变化。

还有一种情况是长期运行的 Agent。

Agent 会反复使用工具、读取文件、更新上下文。它的工作负载不仅包含文本生成，还包含工具调用等待、上下文管理、缓存复用以及可能发生的重新 Prefill。

这种场景下，推理内核本身的速度只是总任务耗时的一部分。

如果系统有很长时间都在等待外部工具，那么把 Decode 提速 10%，不一定能够让任务完成时间缩短 10%。

所以，我认为对长上下文优化的评价，应该逐渐从固定长度的合成测试，走向真实请求轨迹。

还有一个 GAAC 论文自己发现的细节值得关注。

它的指数编码需要提前校准常见指数区间。虽然编码是无损的，但指数分布如果发生变化，更多数据就可能需要采用更高位宽或者原始模式。

论文附录研究了 RoPE 带来的位置分布变化。

在 Qwen3-8B 的实验中，如果只用不超过 8K token 的短上下文进行校准，再把同样的编码窗口应用到 32K 上下文，部分 Key 数据的额外存储需求会随着位置增长明显增加。

使用 32K 上下文校准后，这种增长得到缓解。

这说明，即使算法能够保证数值无损，也不意味着压缩率对所有工作负载都完全稳定。

长期运行的推理系统，面对的是不断变化的上下文内容、长度和请求分布。

一个在固定测试条件下表现良好的压缩格式，部署后还要经受不同长度和数据分布的考验。

这里真正值得测试的，不只是某个时刻压缩了多少字节，而是系统持续运行后，缓存布局、编码效率和请求延迟会怎样变化。

## 九、如果重新评价本地推理，我会先把指标拆开

读完这些实验，我越来越觉得，本地推理性能需要更细致的评价方式。

至少不能再把“可以运行”和“运行得流畅”混成同一个结论。

如果要评价一种新的 KV Cache 压缩方案，我会先看容量。

它究竟减少了多少原始数据？运行时真正释放了多少内存？节省的空间能否容纳更长的上下文，或者更多并发请求？

同时，还要把模型权重、KV Cache 和临时工作区分开。

压缩某一部分数据，并不代表整个进程的内存使用量会同比下降。

第二个问题是延迟。

我更希望看到明确区分的 TTFT、ITL 或 TPOT，而不是只有一个平均 tokens/s。

TTFT 衡量从请求开始到第一个 token 出现需要多久。它受到 Prefill、排队和调度等因素影响。

ITL 衡量连续输出之间的时间间隔，TPOT 则通常从请求层面衡量每个输出 token 的平均耗时。两者有关联，但统计口径并不完全相同。

对于实时聊天，首 token 等待和持续输出的稳定性都很重要。

单纯提高 Decode Kernel 的速度，只解决了其中一部分问题。

第三个问题是并发吞吐。

这里需要同时记录 Batch Size、上下文长度、输出长度、内存预算和聚合吞吐。

更关键的是，应该至少提供两种比较：

一种保持相同 Batch，看单步延迟是否真正下降。

另一种保持相同内存预算，允许系统增加并发，看它能否处理更多请求。

GAAC 把这两个实验分开，是我认为它的数据比较有参考价值的原因之一。

但如果要进一步评价实际部署效果，我还希望加入请求排队时间、P50/P95/P99 延迟，以及满足服务延迟目标的 Goodput。

这些指标能够帮助我们判断：系统虽然生成了更多 token，是否也让更多请求在合理时间内完成。

最后还有两个不能忽略的因素。

一个是输出质量。对于有损 KV 量化，必须验证精度变化是否影响具体任务。对于无损压缩，也需要确认实际计算路径与基线的数值行为。

另一个是功耗和能耗。

有些优化用额外计算换取更少的数据搬运，理论上可能降低总执行时间，但是否节能，还要看硬件功率、运行时间和整个系统的工作状态。

GAAC 目前没有提供功率和能耗测量，因此还不能把它的速度收益直接转换成能效收益。

尤其对于 MacBook 这类移动设备，性能并不是唯一目标。温度、持续功耗和电池续航，也会影响一项推理优化是否真正有用。

论文中的 Apple M4 实验提供了一个不错的起点。

作者用 Metal 实现了压缩 KV 的注意力路径。对于单序列、64K 上下文，注意力内核加速约 1.10 倍；在 8 条并发序列、64K 上下文时，最高达到 1.25 倍。

但这些都是注意力内核结果。

它们还不能告诉我们，一个完整运行在 Mac 上的本地模型，在真实聊天、代码分析或 Agent 任务中究竟会快多少。

如果要把这个实验推进到真正的本地应用，我更希望看到基于完整推理框架的对照测试，尤其是单请求、不同上下文长度和持续运行场景下的结果。

对一台实际使用的电脑来说，这些结果往往比单个 Kernel 的峰值加速更有参考价值。

## 十、模型推理的优化目标，正在从计算转向整条执行路径

回头看这些技术，会发现一个很有意思的变化。

早期讨论大模型推理，我们往往集中在模型规模、参数精度和 GPU 算力上。

这些因素当然重要，但模型一旦进入长期运行的服务环境，问题就变得复杂了。

PagedAttention 解决的是缓存分配和管理效率。

FP8 KV Cache 通过降低数据位宽，减少内存占用和访存量，同时引入新的数值精度与内核实现问题。

GAAC 则进一步利用原始数值中的冗余，在不改变 BF16 KV 表示的前提下，让压缩数据能够直接进入注意力计算。

这些方法的共同点，是不再把推理性能简单等同于模型需要多少次乘加运算。

数据在什么地方、以什么格式保存、什么时候被读取、能否在片上直接消费，以及请求如何组织，都会影响最终性能。

但我不认为这意味着计算优化已经不重要了。

更准确地说，推理系统越来越需要联合考虑计算和数据移动。

一项局部优化能不能转化为整体收益，取决于它是否触及了真正限制系统性能的那条路径。

如果瓶颈在权重读取，压缩 KV 的收益就有限。

如果瓶颈在长上下文注意力，减少 KV 流量可能更有效。

如果瓶颈在内存容量和并发调度，节省缓存空间可以带来比单请求加速更明显的系统收益。

如果瓶颈在工具调用或请求排队，那么进一步优化 GPU 内核，未必是最优先的工作。

这也是为什么同样一项技术，在单用户聊天、多人推理服务和多 Agent 系统中，可能得到完全不同的评价。

它没有一个脱离工作负载的统一加速比。

工程上真正应该追求的，也不是把某项指标做到最大，而是在确定的硬件和工作负载下，找到限制整体效率的主要因素。

对于本地模型部署来说，这个判断尤其重要。

我们不可能无限增加内存，也不可能随时更换更强的 GPU。有限资源如何在权重、缓存、计算和并发请求之间分配，直接决定了设备的使用体验。

有时候，多节省一点缓存，最大的价值是让一个原本放不下的任务能够运行。

有时候，它让长上下文生成更快。

还有时候，它只是让系统能够同时服务更多任务。

这三种收益都真实存在，但它们不是同一件事。

## 结语

GAAC 最后给我的启发，并不是“KV Cache 应该使用无损压缩”，更不是“未来所有本地模型都能因此提速 20%”。

它真正展示的是一种工程权衡。

作者接受了额外的数据重建计算，换取更少的 KV 内存访问；又通过缓存管理，把部分容量节省转化成更高的并发能力。

最终，我们看到约 26% 的驻留 KV 内存节省、4%–15% 的完整 Decode Step 加速，以及 13%–29% 的聚合吞吐提升。

每个数字都有自己的意义，也都有对应的实验条件。

其中最值得注意的，是这些数字之间不存在固定比例。

一项压缩技术的价值，不能只看它省下了多少字节。一个计算内核的价值，也不能只看它比基线快了多少倍。最终还是要看，它到底改善了用户最在意的哪部分体验。

过去我们部署本地模型，经常先问一台机器能不能把模型装下。

现在，随着模型量化和本地推理框架越来越成熟，这个问题已经不够了。

我更关心的是：装下之后，数据是否还在反复搬运？计算单元是否真的得到了充分利用？多个请求是否在争夺同一份有限的资源？所谓的性能提升，又究竟发生在单个算子、一次生成步骤，还是完整的用户任务上？

模型装得下，只能说明容量足够。

至于它能不能跑得快，还需要看整个推理系统怎样工作。

- GAAC 以 [arXiv:2610.38210v1](https://arxiv.org/html/2610.38210v1) 为准，作者为 University of Notre Dame 的 Yipin Guo、Arun M George、Siddharth Joshi；论文声明 CC BY 4.0。Table 1 的编码压缩比、附录 D 的驻留内存、Figure 5 的内核、Figure 6 的完整 decode step 和 Table 2 的等 KV 预算聚合吞吐属于不同口径。
- 1.406 倍压缩约节省 28.9% 编码体积；约 26% 指驻留 KV，而非全进程内存。1.22 倍加速意味着速率约增加 22%、耗时约下降 18%。完整步骤的 1.04–1.15 倍不是耗时下降 4%–15%。
- Table 5 为 64K decode-attention 内核计时：1359.3→1114.2 μs，KV 读取少 294.3 μs，计算多 49.2 μs；先解压方案为 2290.1 μs。Table 4 的 187.1→526.7 μs 是独立解码消融，不能与前者当作同一计时范围。
- Figure 5 在 Qwen3-8B 的 32K/64K/128K 内核加速为 1.31/1.27/1.25 倍，不能把长上下文优势写成内核倍率必然单调上升。Figure 6 的完整步骤收益与这一曲线不同。
- 无损保证针对原始 KV 位模式，不应扩展成不同浮点内核的注意力输出或完整生成序列逐位一致。校准失配影响编码效率和回退，不引入编码近似。
- 19.0/2 与 22.8/3 只是聚合吞吐的算术平均，不是请求 ITL 的实测，更不能证明同 batch 回归。多 Agent 排队收益和 goodput 是部署分析，不是 GAAC 已完成的 Agent 轨迹实验。
- 32 层、8 个 KV head、128 head dim 的 8 GiB 是假设架构；8 GiB 在 1 TB/s 下约 8.6 ms 是理想传输下限，既不是 DGX Spark 实测带宽，也不是 Table 5 内核耗时。论文报告 DGX Spark 实测带宽约 240 GB/s。
- vLLM FP8 报告的硬件与配置不同，不能与 GAAC 横向排名；FP8 额外无损压缩不恢复初始量化损失。Apple M4 只有注意力内核结果；论文没有整机能耗数据。
